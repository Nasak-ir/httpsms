# معماری

طبق [سند پروژه](../NASAK_SMS.md)، درخواست API به صف و گوشی Android متصل می‌شود؛ PostgreSQL، Redis و FCM در جریان توصیف‌شده نقش دارند و دریافت پیام می‌تواند webhook ایجاد کند. پاسخ موفق ارسال به معنی ورود به صف است، نه تحویل نهایی. این fork از httpSMS است؛ مجوز و attribution مخزن حفظ شوند.

## وضعیت پیام در مدل

در [مدل پیام](../../api/pkg/entities/message.go) وضعیت‌های `pending`، `scheduled`، `sending`، `sent`، `delivered`، `failed`، `expired`، `received` و `deleted` تعریف شده‌اند. `sent` و `delivered` وضعیت مجزا هستند؛ `received` برای پیام ورودی/تماس ازدست‌رفته نیز استفاده می‌شود. فیلدهای زمان، شمار تلاش و شناسهٔ درخواست اختیاری در همان مدل آمده‌اند. وجود این فیلدها به‌تنهایی اثبات ترتیب نهایی رخداد، تحویل فیزیکی، یا قرارداد کامل idempotency نیست؛ رفتار مسیر و نسخهٔ فعال باید جدا بررسی شود.

رابط [PushQueue](../../api/pkg/services/push_queue_service.go) عملیات enqueue را تعریف می‌کند؛ انتخاب پیاده‌سازی و پیکربندی واقعی باید از محیط تأیید شود. گراف موجود در ۲۹ اکتبر برای یافتن این منابع پرس‌وجو شد؛ گراف خود جای بازبینی کد و آزمون runtime نیست.
